# 模型配置迭代 · 需求分析（v2）

- 状态：需求分析，**待确认，未进入开发**
- 日期：2026-10-27
- 涉及模块：管理平台 · 模型配置（前端 `ModelsView`）/ 服务端 `model-configs`、`llm-client`、`responses-image.client`、`photo-optimize`
- 需求来源：4 条迭代要求（合并配置 / 拉取模型 / 推理强度 / 收敛 OpenAI）

---

## 0. 一句话结论

本次的核心动作不是"删掉一张卡片"，而是把**「用哪个模型」的表达方式**从"配置类型（llm / image-gen / dify）"改为"**一份 OpenAI 凭据 + 默认模型 + 生图模型 + 推理强度**"。需要先定清楚的三件事：合并后生图模型怎么配（已确认用户手动填、空则 `gpt-image-2`）、推理强度档位如何映射到上游（已确认收敛为三档）、历史三类配置如何迁移且可回滚。

### 0.1 已确认决策（2026-10-27）

| 编号 | 决策项 | 结论 |
| --- | --- | --- |
| D1 | 合并后模型怎么配 | **一份配置**：对话/分析/生图同卡片、同凭据；`default_model` 负责对话与分析，`image_model` 负责出图（见 D8） |
| D2 | 推理强度档位 | **改为三档「低 / 中 / 高」**，对应 `low / medium / high`。⚠️ 原需求为四档（最高/高/中/低），此处为**需求变更**，因上游无「最高」取值 |
| D3 | Dify 配置 | **彻底删除** `dify` 类型与数据（含旧表行），关联两个未实现工具维持 501 |
| D4 | Base URL | **允许自定义**，默认 `https://api.openai.com/v1`，文案标注"仅 OpenAI 兼容协议" |
| D5 | 模型拉取结果 | **不缓存**，仅当前页面内存显示，刷新即清空、需重新拉取 |
| D6 | 推理强度默认值 | **默认「中」**（`medium`），非 reasoning 模型自动忽略该参数 |
| D7 | 保存前验证 | **不做**任何保存前校验/连通性探测；默认用户已知要求，改为配置页常驻「模型能力要求」告知；移除能力测试入口 |
| D8 | 生图模型来源 | **用户手动配置**（同卡片非必填项）；留空则回退系统默认 `gpt-image-2`；库中存 `NULL` 以保留"跟随默认"语义 |

> D3 涉及不可逆数据删除：实施时先备份 `server-node/data/hftools.db`，再执行删除，并在迁移日志中记录被删行内容（不含明文 key）。

## 1. 现状盘点（以代码为准）

### 1.1 配置模型

`model_configs` 表以 `type` 为主键，一类型一行（`server-node/src/db/index.ts:34`）：

| type | 用途 | 消费点 | 存储字段 |
| --- | --- | --- | --- |
| `llm` | 对话/多模态分析 | 照片点评（`photo-review.service.ts:57`）、提示词优化（`prompt-optimize.service.ts:68`）、照片 AI 优化阶段一（`photo-optimize.service.ts:167`） | base_url / api_key / models[] |
| `image-gen` | Responses API 生图 | 照片 AI 优化阶段二（`photo-optimize.service.ts:405`）、能力测试（`admin.routes.ts:92`） | 上述 + image_model |
| `dify` | 工作流编排（未实现） | 仅 `ai.ts:14` 的 `git-trending` / `company-research` 映射，校验配置后返回 501 | base_url / api_key / models[]（应用标识） |

### 1.2 已存在但未生效的能力

- `models: string[]` 实际只取 `models[0]`（`llm-client.service.ts:46`），"多模型"从未生效 —— 本次合并正好可以把它收敛成单个 `default_model`。
- `image_model` 仅 `image-gen` 语义，作为 Responses 请求里 `image_generation` tool 的模型参数（`responses-image.client.ts:86`）。
- 请求体目前只有 `{ model, messages, stream: false }`，**没有任何 reasoning 参数**。

### 1.3 痛点（与 4 条需求的对应关系）

| 痛点 | 现状表现 | 对应需求 |
| --- | --- | --- |
| 同一家 OpenAI 要填两遍 key，改地址/换 key 要改两处，容易错配 | llm 与 image-gen 各自独立存凭据 | 要求 1 |
| 模型名靠手填，拼错只有在真实调用时才暴露（上游 400/404） | `el-select allow-create` 手工输入 | 要求 2 |
| 长文本任务与轻量任务共用一档推理预算，质量/成本不可调 | 无 reasoning 参数 | 要求 3 |
| 类型概念外溢到 service / 路由 / 前端表单 / 错误文案 | `MODEL_TYPES` 三值贯穿全链路 | 要求 4 |

## 2. 目标与非目标

### 2.1 目标（可衡量）

| 编号 | 目标 | 衡量方式 |

| G1 | 配置面从 3 张卡片 10 个输入项收敛为 **1 张卡片 ≤5 个输入项** | 页面字段数；配置一次成功率 100%（无手填模型名错误） |

## 3. 需求拆解

### R1 合并文本与生图配置，全局生效（P0）

**目标行为**：只保留一份配置对象，被所有 AI 调用共享（不再有"类型"概念）。

```
{ provider: 'openai', base_url, api_key, default_model, image_model, reasoning_effort, updated_at }
```

**字段构成（1 张卡片 / 5 个可编辑项）**

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| Base URL | 是 | 默认 `https://api.openai.com/v1` |
| API Key | 是（首次） | 留空表示不修改 |
| 默认模型 `default_model` | 是 | 对话 / 多模态分析 / 驱动 Responses 生图调用的主模型 |
| 生图模型 `image_model` | 否 | **用户手动配置**；为空则回退系统默认 `gpt-image-2` |
| 推理强度 `reasoning_effort` | 是 | 低/中/高，默认中 |

**关键设计点（已按 D8 修正）**：合并的是"配置入口"，不是"把两个模型压成一个"。生图模型作为同一张卡片里的一个非必填字段存在，因此：

- `default_model` 只需承担对话、图片输入分析与 Responses 主模型职责，**不再要求它自己具备出图能力**
- `image_model` 承载实际出图，为空时运行时回退 `gpt-image-2`
- 两者仍是一份凭据、一次保存、一处维护 —— 不构成"文本/生图两类配置"

**验收标准**
- [ ] 管理平台模型配置页只有一张卡片，无"文本模型 / 生图模型 / Dify"分区
- [ ] `GET /api/admin/model-config` 返回单个对象（不再是数组）
- [ ] 照片点评、提示词优化、照片优化（阶段一 + 阶段二）四条链路均从该配置取凭据
- [ ] 未配置时四条链路报错文案统一为"模型服务尚未配置"
- [ ] 生图模型为**非必填**输入项，占位提示为 `gpt-image-2`，留空可正常保存
- [ ] 生图模型留空时，请求体中的出图模型回退为 `gpt-image-2`
- [ ] 生图模型留空时**数据库存 `NULL`**，不把 `gpt-image-2` 写死（保留"跟随系统默认"语义）
- [ ] **点击保存不产生任何上游请求**（无探测、无测试调用、无费用），可由服务端日志验证
- [ ] 配置页常驻展示「模型能力要求」告知块（内容见 §3.5）

**技术注意（实现前需确认，属本次顺带修正项）**
现有生图请求把生图模型放在**顶层** `image_model` 字段（`responses-image.client.ts:104-105`），而 OpenAI 的写法是写在工具定义里：`tools: [{ type: 'image_generation', model: '<image_model>' }]`。本次既然要显式配置生图模型，应一并纠正为工具内参数，否则可能出现"配了但不生效、上游按默认模型出图"的静默偏差。**已确认：只保留标准写法，不做顶层双写**（避免"到底哪个生效"不可解释）。

### R2 拉取并解析上游模型，显示并支持复制（P0）

**目标行为**：一次点击拿到上游可用模型清单，替代手填。

**流程与契约**
1. 前置条件：`base_url` 与 `api_key` 已保存（**以已保存配置为准**，表单有未保存改动时按钮禁用并提示"请先保存配置"）
2. 服务端代理 `GET {base_url}/models`，`Authorization: Bearer <key>`，超时 10s，不自动重试（**必须服务端发起**：避免 key 出现在浏览器、规避 CORS）
3. 解析 `data[].id`：去重、排序、过滤噪声模型（embedding / tts / whisper / moderation / audio / realtime / transcribe 等），保留对话与图像类（`gpt-*`、`o1/o3/o4*`、`chatgpt-*`、`gpt-image-*`、`dall-e-*`）
4. 前端展示：可搜索的模型列表，每项含**复制按钮**（复制 `id`），另提供"复制全部"（换行分隔）
5. 失败分类：401/403 → key 无效；网络不可达 → 502；返回非预期结构 → 解析失败；超时 → 504；空列表 → "上游未返回可用模型"

**已确认：不做缓存（D5）**
- 拉取结果**只存在于当前页面内存**，不写库、不写 localStorage/sessionStorage
- 刷新或重新进入页面即清空，需重新拉取；这是有意为之，避免"上游已下架但本地还显示"的过期清单
- 后果：每次进入页面要手动点一次拉取（接受）；"默认模型"仍是持久化字段，页面上以已保存值为准回显
- **拉取是可选动作，不是保存的前置条件**：`default_model` 允许直接手填或沿用已保存值，不得因为"本次没拉取"而阻止保存或清空已有值

**待决点（非阻塞）**
- 是否允许用"表单里未保存的新 key"拉取：建议不允许，防止"拉的是 A 套、存的是 B 套"的错配

**验收标准**
- [ ] 未保存配置时点击拉取有明确提示，不发请求
- [ ] 有效配置下拉取成功，展示数量与拉取时间，列表可搜索
- [ ] 单条模型可一键复制，复制内容为纯 `id`
- [ ] 无效 key 返回可读文案，不暴露上游原始报文中的敏感信息
- [ ] 刷新页面后列表清空（不缓存），已保存的默认模型不受影响

### R3 支持设定推理强度（P0）

**目标行为**：三档「低 / 中 / 高」可配置，作为全局默认。默认「中」。

> 原需求为四档（最高/高/中/低）。OpenAI 的 `reasoning.effort` 仅提供 `minimal / low / medium / high`（gpt-5 系列；gpt-5.1 起另有 `none`），"最高"没有对应取值，硬做会出现假档位或文案与语义偏移。已确认收敛为三档。

| 档位 | 上游取值 |
| --- | --- |
| 低 | `low` |
| 中（默认） | `medium` |
| 高 | `high` |

**透传范围**
- `/chat/completions`：`reasoning_effort`
- `/v1/responses`：`reasoning: { effort }`
- 生图请求：**不透传**，由 `image_generation` tool 自行处理，避免影响出图稳定性

**兼容策略（重要）**
- 上游不返回能力元数据，故用**模型名前缀白名单**判定（`o1/o3/o4`、`gpt-5*`）；不在白名单时**不传该参数**，而不是让上游报 400
- 这是**请求期参数整形**，不是保存前校验，也不询问用户（符合 D7）
- 白名单内仍被上游拒绝时，透出可读错误（"当前模型不支持该推理强度"），**不做自动降级重试**（避免一次调用变两次、费用翻倍）

**验收标准**
- [ ] 配置页可选择三档并保存，刷新后回显正确
- [ ] 选择 reasoning 模型时，请求体中能看到对应取值（低/中/高 → low/medium/high）
- [ ] 选择非 reasoning 模型（如 gpt-4o）时，请求体不含该参数且调用成功
- [ ] 页面文案说明"该设置对不支持推理的模型自动忽略"

**验收标准**

- [ ] 前端类型定义、错误文案、日志中不再出现类型后缀

- [ ] Base URL 可编辑并保存成功，非法协议被拒绝

### R5 配置页「模型能力要求」告知（P0，D7）

**定位**：系统**不承担保存前验证**，配置是否可用由用户自行确认。页面必须把要求说清楚，避免"配了但跑不通、不知道该改什么"。

**展示形式**：配置卡片顶部常驻一条 `el-alert`（type=info，不可关闭），首行结论 + 折叠详情；不随保存状态消失。

**建议文案（可直接用于开发）**

> **当前配置要求（系统不做保存前校验，请自行确认）**
> 保存前请确认以下条件，系统不会代为验证，也不会在保存时发起任何请求。
>
> 1. **接口协议**：仅支持 OpenAI 兼容接口，需同时提供 `/v1/chat/completions` 与 `/v1/responses`
> 2. **默认模型**：需支持多模态图片输入（照片点评、照片优化分析），并能作为 `/v1/responses` 主模型调用图片工具
> 3. **生图模型**：填写上游支持的图像生成模型；留空则按 `gpt-image-2` 出图。填错或上游不支持时，照片 AI 优化会失败
> 4. **推理强度**：仅对推理模型（`o1`/`o3`/`o4`/`gpt-5*`）生效，其他模型会自动忽略该参数
> 5. **API Key**：需具备上述两个接口的调用权限与额度；使用中转地址时请自行确认其兼容性，以及是否支持所填的生图模型
> 6. **验证方式**：保存后到对应工具页发起一次真实调用，失败信息会明确指向具体原因

**验收标准**
- [ ] 告警块常驻可见，不依赖滚动/悬停才出现
- [ ] 文案明确写出"系统不做保存前校验"
- [ ] 文案包含"默认模型需支持多模态输入并能驱动图片工具"与"生图模型留空按 gpt-image-2 出图"两条关键约束
- [ ] 页面不存在"保存时自动测试/自动校验"类按钮或流程

**关于原「测试 Responses 能力」按钮**
- 现有页面有一个手动测试按钮（`admin.routes.ts:90`）。按 D7 定位，**本期移除**：它会让用户误以为"系统会帮我验证"，且需要一次真实生图调用（有费用）。
- 排错改由运行时错误提示承担；如后续确认需要，再加"可选手动测试"，且必须明确标注"非保存前置、会产生调用费用"。

## 4. 数据与迁移方案

**新表（单行）**

```sql
CREATE TABLE IF NOT EXISTS model_config (
  id INTEGER PRIMARY KEY CHECK (id = 1),
  provider TEXT NOT NULL DEFAULT 'openai',
  base_url TEXT,
  api_key TEXT,              -- 沿用 AES-256-GCM 密文
  default_model TEXT,
  image_model TEXT,          -- 可空；NULL 表示跟随系统默认（gpt-image-2）
  reasoning_effort TEXT,     -- low | medium | high（默认 medium）
  updated_at TEXT
);
```

> 模型清单不落库（D5 已确认）：表结构**不设** `available_models` / `models_fetched_at`，拉取结果仅存前端页面内存。

**迁移规则（启动时执行，幂等）**
1. 新表无数据时，读旧表 `type='llm'` 行作为主基准
2. `api_key` **密文直接搬运**，不做解密再加密（避免 `SECRET_KEY` 变更导致迁移失败或密钥损坏）
3. `default_model` 取 `llm.models[0]`，为空则回退 `image-gen.models[0]`
4. `image_model` 取旧 `image-gen.image_model`（有值则迁入）；旧 `image-gen.models[0]` 若与 `default_model` 不同，写入迁移日志提示人工确认，**不自动猜测**
5. `DELETE FROM model_configs WHERE type = 'dify'`：删除前先把该行摘要（不含明文 key）写入日志；执行前需备份 `server-node/data/hftools.db`
6. 旧 `llm` / `image-gen` 行保留只读不删，作为回滚与追溯依据；不双写
7. 迁移只做一次，日志记录来源行与时间

**接口变更**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/admin/model-config` | 返回单个配置（脱敏 key） |
| PUT | `/api/admin/model-config` | 保存（key 留空不修改；`image_model` 传空串/null 表示清空、回退默认） |
| POST | `/api/admin/model-config/models` | 拉取并解析上游模型 |
| POST | ~~`/api/admin/model-config/test`~~ | **不提供**：不做保存前/主动能力测试（D7） |

> 模型清单接口除了对话模型，也应保留 `gpt-image-*` / `dall-e-*`，用于生图模型字段的候选提示。

> 旧接口 `/api/admin/model-configs/:type` 建议直接替换（仅管理端自用，无外部消费者），不保留双写。

## 6. 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 默认模型不支持多模态输入或无法驱动图片工具 | 照片点评/照片优化失败 | 配置页明示该要求（§3.5）；运行时按错误归类给出可读原因，不在保存时探测 |
| 生图模型填错或目标地址不提供该模型 | 照片优化出图失败（上游 404/400） | 拉取列表保留 `gpt-image-*` 供选择；留空走默认 `gpt-image-2`；错误文案点明是"生图模型"问题 |
| 生图模型参数位置写错（顶层 vs tool 内） | 配置看似生效但实际按默认出图 | 本次纠偏为 `tools[0].model`，验收时检查实际请求体 |
| reasoning 参数导致非 reasoning 模型 400 | 全部文本链路失败 | 前缀白名单 + 不传策略 + 不做静默重试 |
| 拉取接口被用于任意 URL 请求（SSRF） | 内网探测风险 | 仅使用**已保存**的 base_url，不接受请求体传 URL |
| 迁移丢失既有配置 | 上线后所有工具不可用 | 密文直搬、旧行保留、迁移前后打日志、上线前备份 `data/hftools.db` |
| 删除 dify 行为不可逆 | 未来做工作流需重建配置 | 删除前备份 DB + 日志留存摘要 |
| 从"三类配置"变成"单点配置" | 改错 key 影响全部工具 | 本次接受（单机自用）；多套配置列入 NG2 后续议题 |
| 模型列表噪声（embedding/tts 等） | 选错模型 | 前缀过滤 + 列表标注类型 |
| 用户不看告知块，配错模型/模型不支持图像工具 | 首次调用才暴露 | 定位接受（D7：不做保存前校验）；靠常驻告警 + 运行时错误文案把原因说透，减少反复试错 |
| 移除能力测试按钮后缺少自查手段 | 排障路径变长 | 运行时错误区分"鉴权/模型不存在/不支持图片工具/限流/超时"并给出对应改法 |
